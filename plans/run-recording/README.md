# Run recording plan

Status: Draft specification; implementation has not started. Source anchors were inspected on 14 October 2026.

## Product decision

Eigent remains a headless product. Recording is an optional Brain capability with an Electron adapter for local capture. The Brain owns commands, lifecycle, Run association, storage policy and clip metadata. Electron supplies OS interaction, the media stream, encoding and a bounded local spool. React is one client of the same contract; a mounted Session page must not be required to control an already authorized recording.

This follows the local-folder boundary: Electron supplies the native picker while the Brain owns Space binding and filesystem state. Electron is the only production capture provider in this scope. A Brain without that adapter still boots, executes Tasks and serves recording metadata; starting capture returns a typed unavailable result. Headless operation does not imply that desktop pixels exist without a connected source or required OS consent.

## Outcome and scope

Users can save useful footage of Eigent working in the selected Space's folder, associated with the existing `space_id`, `project_id`, `task_id`, `run_id` and `attempt_id`. Visible wording follows Space → Session → Task. Backend Project identifiers, translation keys and persisted contracts remain unchanged.

The first release provides:

- Opt-in silent recording of the Eigent application window associated with a Run.
- One active capture per desktop provider; a second start is rejected rather than queued or mixed.
- Start and stop through a headless API, also consumed by the desktop UI.
- An app-wide recording indicator with a stop control, visible on every page while capture is active.
- Automatic stop on Run termination, with independent recording finalization.
- A playable local clip and a manifest in the bound Space folder.
- Backend clip listing and reuse of the existing Files/video preview.
- Bounded disk writes, truthful interrupted states and crash recovery.

Microphone/system audio, entire-desktop capture, third-party application windows, cloud uploads and automatic recording of every run are outside the first release. Recording the workflow is separate from rendering video generated by the Task.

MP4 is the desired editing format, subject to the codec/muxer spike. The spike tests Chromium's native MediaRecorder MP4 output first, which may remove the need for a separate encoder. If native capture produces WebM, retain a correctly labelled original that has been made seekable. Never rename WebM bytes to `.mp4` or claim an export that did not succeed.

Recording captures whatever the Eigent window shows, including other Sessions, Settings and pages open in the embedded browser. Capture continues when the user navigates away from the Session that started it, so the indicator and stop control are app-wide rather than Session-only.

After normal clips work, add an opt-in rolling buffer and **Save last 30 seconds**. Event bookmarks can then help select interesting tool steps. These features use the same provider/API contract and do not require a new video editor or screen-recording SDK.

## Governing contracts

Read the full [design guideline](../../docs/design-system/design.md) and [product terminology](../../docs/product-terminology.md) before implementation. Use the [design viewer](../../docs/design-system/index.html) as the visual reference. The start control belongs to the existing Session surface and the active-recording indicator to the app-wide top bar; the API remains usable without either.

"Run" is a backend term, not UI wording. Visible copy and user-facing folder names must not introduce it.

This plan adds documentation only. It does not implement recording, change dependencies, request capture permissions or change runtime/UI behavior.
