# Design System Migration Plan

> **Decision:** the new system plan passed design review. Implementation is a
> staged migration, not a repository-wide replacement. Each phase must leave the
> application releasable and the compatibility layer measurable.

## Operating model

The approved source contract is
[`../new-design-system-plan/DESIGN.md`](../new-design-system-plan/DESIGN.md).
Current usage is regenerated by
[`../scripts/build-token-usage-report.mjs`](../scripts/build-token-usage-report.mjs).
Before and after every phase:

1. Run `npm run build:design-system` and archive the generated usage counts in
   the phase PR.
2. Run `npm run check:design-system`, focused component tests, type checking,
   and the phase's visual matrix.
3. Do not add new legacy aliases or raw exceptions. Any necessary exception
   needs an owner, scope, reason, and removal gate.
4. Keep compatibility aliases one-way: legacy name to approved semantic token.
   Never let new tokens depend on a legacy alias.
5. Land phases independently. A rollback removes the phase's consumer changes
   while the prior compatibility contract remains valid.

## Phase 0 — Freeze and baseline

**Entry:** latest workforce base is integrated and the worktree is understood.

**Work:**

- Generate the token/CSS usage report and classify every unmapped alias.
- Record light and dark screenshots for app shell, chat, settings, files,
  browser, terminal, forms, dialogs, Markdown, and destructive confirmation.
- Add representative keyboard-focus, disabled, selected, hover, and loading
  states to the visual gate.
- Freeze new legacy token names and one-off component shadows, radii, and type
  utilities through lint or a reviewed allowlist.

**Exit:** the generated report is reproducible, visual fixtures are named, and
every current exception has an owner. **Rollback:** documentation only; no
runtime change.

## Phase 1 — Stabilize the Tailwind 4 foundation

**Entry:** Phase 0 baseline is stored.

**Work:**

- Keep the configuration loadable as ESM and preserve explicit CSS layer order.
- Use the Tailwind 4 PostCSS package and intentional source paths only.
- Replace removed utilities reported by the scanner.
- Verify `space-*`, `divide-*`, arbitrary transitions, transforms, and important
  utilities on their real components.
- Keep Preflight disabled until semantic elements have explicit app defaults.
- Extend `tailwind-merge` for owned elevation classes, or expose elevation only
  through primitive props.

**Exit:** the Tailwind sentinel compile, app build, type check, and visual
baseline pass with no missing design-system utilities. **Rollback:** restore the
previous CSS entry/PostCSS/config together; do not mix v3 and v4 delivery paths.

## Phase 2 — Establish generated token foundations

**Entry:** Tailwind delivery is stable.

**Work:**

- Add the reviewed reference, semantic, component-recipe, and exception source
  files.
- Generate CSS variables, Tailwind exposure, TypeScript names, and viewer data
  from the same manifest.
- Add validation for unknown references, cycles, invalid units, duplicate public
  aliases, contrast, and required state coverage.
- Retain the current color engine behind a compatibility adapter while the new
  Accent, Neutral, Ink, Hairline, Feedback, and Category contracts are emitted.

**Exit:** deterministic generation has a clean-tree check and all six Eigent
themes produce complete light/dark token sets. **Rollback:** consumers still
resolve through compatibility aliases; remove the new generator outputs.

## Phase 3 — Migrate shared primitives first

**Entry:** new tokens are available without changing feature call sites.

**Order:**

1. Typography and semantic text primitives, including the adjustable 13px text
   and code seeds and the 10/11px metadata role.
2. Lucide icon wrapper with the 16px/1.25px and 24px/1.5px optical contracts;
   Morphicons only for approved state-changing pairs.
3. Button variants: text, ghost, outline, borderless secondary, primary, and
   semantic confirmation tones. Button horizontal padding is twice vertical
   padding, and icons follow the optical-size contract.
4. Field, select, textarea, row, and header recipes. Key header rows are 40px or
   48px; the canonical 40px row composes a 28px action.
5. Dialog, popover, tooltip, card, navigation, and Markdown primitives.

**Exit:** each primitive has a state/size/theme matrix, semantic HTML and label
associations, keyboard tests, and no feature-specific selector that silently
resizes children. **Rollback:** switch that primitive back to its compatibility
recipe without removing the token foundation.

## Phase 4 — Migrate color consumers by intent

**Entry:** shared primitives consume new recipes.

**Work:**

- Migrate direct high-confidence mappings from the generated migration diff.
- Review medium-confidence surface mappings in their rendered context.
- Replace legacy component-color aliases at call sites with Accent, Neutral,
  Ink, Hairline, Ring, Feedback, or Category intent; do not recreate a new
  component-color namespace.
- Use the Eigent theme as the default matrix seed (`#1d1d1d`) and verify that
  hover/selected remain in the same perceptual family in light and dark mode.
- Keep Feedback colors for outcomes, not ordinary interaction states.

**Exit:** no approved component uses a legacy fill-fill alias; state contrast and
perceptual gates pass for all six themes. **Rollback:** restore the affected
feature's compatibility alias, not the old global generator.

## Phase 5 — Migrate geometry, shape, border, and elevation

**Entry:** core components own their color and state recipes.

**Work:**

- Replace numeric spacing in shared layouts with named control, inset, stack,
  and row recipes before touching isolated feature spacing.
- Consolidate radius roles and keep rounded-full for approved clickable pills;
  preserve explicit native/browser exceptions.
- Migrate borders, separators, and focus rings as separate semantic layers.
- Route elevation through owned semantic levels backed by `shadow-plugin`.
- Check focus-ring and shadow overflow in fixed-height rows and clipped panels.

**Exit:** scanner counts fall to the documented exception allowlist, key 40/48px
headers remain aligned, and native/DOM radii match. **Rollback:** revert one
recipe family at a time; token aliases stay available until the phase closes.

## Phase 6 — Complete content, accessibility, and application migration

**Entry:** foundations and high-traffic primitives are stable.

**Work:**

- Unify Markdown renderers onto the approved Standard and Compact profiles.
- Replace styled text `div`/`span` elements where semantic headings,
  paragraphs, labels, or descriptions are required.
- Migrate feature surfaces in vertical slices: app shell, chat, files/session,
  settings, browser/terminal, triggers/workflow, then remaining surfaces.
- Verify Windows/macOS/Electron behavior, zoom, reduced motion, high contrast,
  keyboard-only flow, and coarse-pointer hit areas.

**Exit:** all production surfaces are assigned to an approved recipe or an
owned exception, with no accessibility regression. **Rollback:** vertical slices
can revert independently.

## Phase 7 — Remove compatibility and enforce the contract

**Entry:** two releases show no compatibility-alias regressions.

**Work:** remove unused legacy variables/config aliases, close temporary
allowlists, make generation and usage checks required in CI, and update the
viewer from implementation evidence.

**Exit:** legacy counts are zero except approved runtime exceptions; generated
files are deterministic; the plan, token manifest, primitives, and CI checks
agree. **Rollback:** restore only the last compatibility release; do not revive
parallel sources of truth.

## Required evidence per implementation PR

- Generated usage-report delta with explanations for every increase.
- Light/dark and affected-theme screenshots for default, hover, selected,
  disabled, and focus-visible states.
- Focused component tests plus `npm run type-check` and
  `npm run check:design-system`.
- Explicit exception changes, deprecation removals, and rollback boundary.
- Tailwind 4 risk checklist when CSS config, utility syntax, plugins, or source
  detection changes.
